## 1. Общее описание

**Zabron** — веб-сервис для онлайн-бронирования заведений отдыха и досуга в Астане, Казахстан. Агрегатор, позволяющий клиентам находить и бронировать слоты в банях, спа-комплексах и других заведениях, а владельцам — управлять своими объектами и принимать/отклонять заявки.

**Текущее состояние:** MVP-стадия. Проект функционально завершён в базовых сценариях, но имеет архитектурные ограничения, критичные для масштабирования.

## 3. Архитектура хранения данных

### Критически важный момент: двойное хранилище

Проект использует **два независимых хранилища**, и это главная архитектурная особенность, которую нужно понять с первого дня:

#### 3.1 localStorage (основное, `banya_*` ключи)

Всё, кроме синхронизации статусов броней, живёт в localStorage браузера клиента:

| Ключ | Содержимое |
|---|---|
| `banya_users` | Все зарегистрированные пользователи (включая пароли в открытом виде!) |
| `banya_current_user` | Текущий авторизованный пользователь |
| `banya_bathhouses` | Все заведения |
| `banya_cabins` | Все кабинки/помещения |
| `banya_slots` | Забронированные слоты |
| `banya_bookings` | Все бронирования |
| `banya_notifications` | Уведомления |
| `banya_geocode_cache` | Кэш геокодирования адресов |
| `banya_guest_id` | Анонимный ID для гостевых броней |
| `banya_seed_version` | Версия seed-данных (текущая: `'24'`) |

**Следствие:** данные хранятся только на устройстве пользователя. Смена браузера или очистка кеша = потеря всех данных.

#### 3.2 Supabase (только бронирования)

В облаке хранится **только одна таблица** — `bookings`. Цель: синхронизация статусов между клиентом и администратором/владельцем.

**Схема таблицы `bookings`:**
```sql
id          uuid PRIMARY KEY
external_id text UNIQUE       -- ID из localStorage
slot_id     text
cabin_id    text
bathhouse_id text
client_id   text              -- может быть guest-UUID или user-UUID
client_name text
client_phone text
guests      integer
booking_date date
start_time  text
end_time    text
status      text              -- 'pending' | 'confirmed' | 'rejected'
comment     text
created_at  timestamptz
updated_at  timestamptz
```

**RLS-политика Supabase:**
- INSERT разрешён всем (anon + authenticated) при status='pending' и заполненных обязательных полях
- SELECT/UPDATE/DELETE — **запрещены напрямую** с браузера
- Чтение и обновление статусов работает только через Edge Function `reservehub-bookings`

#### 3.3 Синхронизация

```
Клиент бронирует → saveBooking() [localStorage] + saveCloudBooking() [Supabase INSERT]
                                                               ↓
Каждые 15 сек: fetchClientCloudBookings() → сравниваем статусы → updateBookingStatus() [localStorage]
                                                               ↓
Администратор: fetchAdminCloudBookings() → updateCloudBookingStatus() → [Edge Function обновляет Supabase]
```

## 5. Роли и права доступа

### 5.1 Гость (неавторизованный)
- Просматривает каталог и страницы заведений
- Может бронировать без регистрации (вводит имя и телефон вручную)
- Видит свои брони на странице `/my-bookings` (привязаны к `localStorage:banya_guest_id`)
- Статусы броней синхронизируются из облака каждые 15 сек

### 5.2 Client (клиент)
- Всё то же, что гость + профиль с email, телефоном и ссылкой
- Брони привязаны к `user.id`
- Видит уведомления о статусах своих броней в шапке
- Кабинет: `/client` — просмотр броней, редактирование профиля

### 5.3 Owner (владелец)
- Доступ к `/owner` — кабинет владельца
- Управляет только своими заведениями (`ownerId === user.id`)
- Может добавлять/редактировать заведения и кабинки
- Просматривает и подтверждает/отклоняет заявки своих заведений
- Видит расписание слотов, может вручную блокировать время
- Базовый CRM: карточка клиента с историей его броней

### 5.4 Admin (администратор)
- Доступ к `/admin` — полная панель
- Видит **все** заведения системы, не только свои
- Управляет любым заведением и кабинками
- Видит все бронирования с фильтрами (по заведению, статусу, дате)
- Синхронизирует статусы броней из Supabase
- Просматривает базу всех клиентов (дедуплицировано по `clientId`)
- **Impersonation:** может войти в систему от имени любого владельца (`loginAs`) и вернуться в свой аккаунт (`returnToAdmin`)

## 6. Функциональность по экранам

### 6.1 Главная страница (`/`)
- Hero-секция с CTA
- 4 категории заведений (Спа и бани, Кафе и рестораны, Развлечения, Активный отдых)
- Блок "Как это работает" (3 шага)
- Блок "Популярные заведения" (первые 3 из базы)

### 6.2 Каталог заведений (`/bathhouses`)
- Фильтрация по 4 категориям через URL-параметр `?category=spa`
- Полнотекстовый поиск по названию и адресу с выпадающими подсказками (до 8 результатов)
- Карта на Leaflet с маркерами для заведений с координатами
  - Клик по маркеру на карте подсвечивает соответствующую карточку
  - Клик по карточке подсвечивает маркер
- Пагинация: `PAGE_SIZE = 18`, кнопка "Показать ещё"
- Автогеокодирование заведений без координат через Nominatim (OpenStreetMap), batching 5 запросов/сек

### 6.3 Страница заведения (`/bathhouse/:id`)
- Фото-галерея: главное фото (21:9) + горизонтальная лента миниатюр
- Поддержка видео (mp4, webm, mov) — автовоспроизведение без звука
- PhotoLightbox — полноэкранный просмотр с навигацией
- Контакты: телефон, email, сайт, Instagram, WhatsApp, 2GIS
- Мини-карта с положением заведения
- Список кабинок с фото, ценой (₸), вместимостью, рабочим временем и длительностью сеанса
- **Основная функция: Календарь бронирования**

### 6.4 Компонент BookingCalendar
Ключевой UI-компонент всего приложения:
1. **Навигация по датам** — стрелки + горизонтальный скролл с chips (на каждом chip — число свободных слотов)
2. **Слоты в виде кнопок** — свободные / занятые (зачёркнутые)
3. **Мультиселект**: клик выбирает слоты, допустимо только последовательное выделение
4. **Ночные смены**: слоты после полуночи (00:00–06:00) корректно сортируются (normalizeMin: +1440 мин)
5. **Диалог подтверждения** (открывается при нажатии "Забронировать"):
   - Выбор времени начала/конца через Select (шаг 30 мин, в пределах свободных диапазонов)
   - Кол-во гостей (1..maxGuests)
   - Комментарий (необязательно, до 500 символов)
   - Для гостей (без авторизации): поля имени и телефона (+7xxxxxxxxxx)
6. **Диалог успеха** — подтверждение с деталями брони

**Алгоритм генерации слотов** (`generateSlotsForCabin`):
- 14 дней вперёд от сегодня
- Равные интервалы от `workStart` до `workEnd` шагом `slotDuration` часов
- Поддержка overnight (endMinutes < startMinutes → endMinutes += 1440)
- Уже существующие в localStorage слоты сохраняют статус `booked`

### 6.5 Процесс бронирования (handleBook)
```
1. Найти все свободные слоты в диапазоне startTime–endTime → bookSlot() каждый
2. Создать объект Booking с status='pending'
3. saveBooking() → localStorage
4. saveCloudBooking() → Supabase INSERT (с catch — показываем toast-предупреждение при ошибке сети)
5. Сохранить уведомление для владельца ("Новая заявка")
6. Сохранить уведомление для клиента ("Ваша заявка принята")
7. submitBookingToGoogleForm() → Google Forms (fire-and-forget, mode: no-cors)
8. Обновить слоты в UI
9. Показать toast + диалог успеха
```

### 6.6 Кабинет владельца (`/owner`)

**Таб "Заявки":**
- Таблица всех броней заведения (дата создания DESC)
- Кнопки "Подтвердить" / "Отклонить" для pending-броней
- При подтверждении/отклонении → `updateBookingStatus()` → localStorage + уведомление клиенту
- При отклонении → автоматически освобождает слот
- Deep link: `?booking=<id>` → автоскролл и пульсирующая подсветка строки
- Кликабельный клиент → мини-CRM диалог с историей всех его броней

**Таб "Кабинки":**
- CRUD кабинок: добавить, редактировать, удалить
- Форма: название, описание, цена (₸), макс. гостей, начало/конец работы, длительность сеанса, до 5 фото

**Таб "Расписание":**
- Таблица слотов выбранной кабинки (14 дней)
- Ручная блокировка/разблокировка слотов

**Таб "Клиенты":**
- Список уникальных клиентов с количеством броней (компонент `ClientsTab`)

**Управление заведениями:**
- Добавить/редактировать заведение: название, адрес, описание, контакты, координаты, до 5 фото
- LocationPicker — интерактивная карта для выбора координат (кликом или drag маркера)

### 6.7 Панель администратора (`/admin`)

Всё то же, что у владельца + расширенные возможности:

## 7. Система уведомлений

## 8. Внешние интеграции

### 8.1 Supabase Edge Function `reservehub-bookings`
Единственный безопасный канал между браузером и облаком. Вызывается с `admin` credentials:
- `listByClient(clientId)` → список броней клиента по его ID
- `action: updateStatus` → обновление статуса брони (только admin)
- Без action → список всех броней (только admin)

### 8.2 Google Forms (fire-and-forget)
При каждом бронировании отправляется запрос на Google Form:
- URL: hardcoded в `src/lib/google-form.ts`
- Поля: имя, телефон, заведение+кабинка, дата, время, кол-во гостей
- Используется `mode: 'no-cors'` — ответ не проверяется
- **Назначение:** резервный канал уведомлений владельцу/оператору

### 8.3 Nominatim (OpenStreetMap geocoding)
- Используется для заведений без координат `lat/lng`
- Запрос: `address + ", Астана, Казахстан"`
- Rate limit: 1 запрос/сек (жёсткий для Nominatim)
- Результаты кэшируются в `banya_geocode_cache` (localStorage)
- Batch-обработка по 5 заведений

## 9. Seed-данные

Файл `src/data/bathhouses-seed.ts` содержит **547 реальных заведений** (bx-0..bx-546) из Астаны:
- Преимущественно бани, сауны, спа-комплексы, гостиничные комплексы с банями
- У большинства заведений есть: телефон, WhatsApp, Instagram
- У части заведений предзаполнены координаты (lat/lng)
- Первые 9 заведений (bx-0..bx-8) имеют реальные фото в `public/photos/` (5 фото × 9 заведений = 45 фото)
- Остальные 538 заведений — без фото

**Seed-версия:** `'24'` (в store.ts: `const SEED_VERSION = '24'`)

При первом запуске или смене SEED_VERSION:
1. Очищаются `banya_bathhouses`, `banya_cabins`, `banya_slots`, `banya_bookings`
2. Записываются 547 заведений
3. Для каждого заведения создаётся **1 кабинка** ("Основная кабинка"): цена 5000₸, до 6 гостей, 10:00–03:00, сеанс 1 ч.
4. Создаются тестовые пользователи: `owner@test.com/123456` и `admin@test.com/admin123`

## 10. Критические замечания и риски

### 🔴 Высокий приоритет

**1. Пароли в открытом виде в localStorage**
- `User.password` хранится как plain text
- При любой XSS-атаке или доступе к DevTools → компрометация всех аккаунтов
- **Что делать:** мигрировать аутентификацию на Supabase Auth

**2. Все пользовательские данные только на устройстве**
- Пользователь зарегистрировался на телефоне → зашёл с компьютера → аккаунт не найден
- Смена браузера/очистка кеша → потеря всех броней, заведений, настроек
- **Что делать:** мигрировать users, bathhouses, cabins, bookings в Supabase

**3. Admin credentials передаются с браузера в Edge Function**
- `user.email` и `user.password` (plain text) уходят в теле запроса к `reservehub-bookings`
- **Что делать:** использовать Supabase Auth + RLS политики

**4. Нет валидации на стороне сервера для большинства операций**
- Все CRUD для заведений и кабинок — чисто клиентский localStorage
- Суперадмин может удалить/изменить любые данные локально без следа

### 🟡 Средний приоритет

**5. localStorage ограничен ~5–10 MB**
- Фото кодируются в base64 и хранятся прямо в localStorage
- Уже реализована защита: при `QuotaExceededError` всплывает toast-предупреждение
- При многих заведениях с фото — реальный риск переполнения
- **Что делать:** хранить медиа в Supabase Storage или CDN

**6. Генерация слотов — только на клиенте, только на 14 дней**
- Слоты не персистируются заранее — генерируются при каждом открытии страницы
- "Занятые" слоты хранятся в localStorage — при очистке кеша все слоты снова станут "свободными"

**7. Дублирование кода Admin/Owner Dashboard**
- AdminDashboard (~700 строк) и OwnerDashboard (~580 строк) содержат практически одинаковую логику форм заведений и кабинок
- Нет общих компонентов для CRUD

**8. Синхронизация полагается на polling, не на realtime**
- Владелец видит новые заявки только через 5 сек (AdminDashboard) или при ручном обновлении (OwnerDashboard)
- **Что делать:** Supabase Realtime subscriptions

**9. Категории и seed-данные — несоответствие**
- Все 547 заведений в seed имеют `category: undefined` (не задана явно)
- В BathhouseList: `(b.category || 'spa') === cat` — все заведения без категории считаются 'spa'
- Фильтр по food/entertainment/outdoor всегда вернёт 0 результатов из seed

### 🟢 Низкий приоритет

**10. Нет реального удаления заведений**
- Нет кнопки удаления заведения (только кабинки)

**11. Нет пагинации в таблицах дашбордов**
